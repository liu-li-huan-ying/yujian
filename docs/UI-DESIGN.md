## 0. 从 v1 到 v2：为什么升级、改了什么

### 0.1 v1 的病：它是文档，不是系统

v1 写得相当完整——三条原则、玉质/玻璃两套材质、排版与间距表、五套窑色皮肤。它的问题不在内容，在**形态**：

- **它声明的刻度从未存在于源码。** §3.3 写了 `--space-1: 4px` … `--space-12: 48px`，而 `tokens.css` 里**一个都没有**。规范停在纸面。
- **它描述了一套已经不存在的令牌系统。** §3.1 / §4 的 `--bg-app`、`--text-primary`、`--bg-elevated` 等 8 个令牌，实测在 `src/` 中**引用数为 0**——代码早已迁到 `--hue-*` 体系（§10 / §11 是后来贴上去的），旧表却留着。读者无法分辨哪一层是活的。
- **它没有强制力。** 于是 40 个组件各自即兴发挥：**22 种字号、24 种圆角、13 种 z-index**。更隐蔽的是**伪令牌**——`var(--hue-hover)`、`var(--hue-border-default)` 这类**从未定义**的变量名，CSS 会**静默丢弃整条声明**：边框不画、背景不变、hover 不动，而**不报错、不警告、测试全绿**。

苹果 HIG / Material 能几十年不散架，靠的不是文档写得更好，是**原则 → 刻度 → 强制**三层闭环。v1 只有第一层。

### 0.2 v2 补的是后两层

| | v1.1 | v2.0 |

## 1. 内核：光只从浮起处透出

### 1.1 一个命题

玉笺的视觉身份不是「毛玻璃 + 大圆角」，也不是「纸质 + 极简」。它是一个更小、可判定的命题：

> **光只从浮起的地方透出来。**
>
> 静止的表面是**玉**——光进去**散开**，所以它温润、实、边缘略亮、不映照身后之物；
> 浮起的表面是**玻璃**——光**穿过**，所以它透、虚、能映出身后之物。

这条命题把「材质」与「空间关系」绑成了一件事：**材质不是风格选项，是高度的读数。**

### 1.2 三条不可让渡的推论

**推论一 · 高度决定材质，用途不决定材质。**
同高度必同材质。禁止因为「这是个设置面板」或「那是个弹窗」就选材质——要问的是「**它叠在内容之上吗**」。

**推论二 · 可读性下限不可让渡。**
「克制」只作用于**装饰**（分隔线、噪点、底衬渐变、边框）；**文字与可交互控件必须达可读性下限**。
v1 的「低对比」是无条件的，代价是：未选中的单选圈只有约 **1.2:1** 对比——用户看不出那是个可选项；强调色按钮上的白字在暗色青瓷上只有约 **2:1**。
**装饰可以退，功能不能退。**

**推论三 · 内容的表面永远平凡。** 见 §1.3。

### 1.3 开光：为什么编辑区必须纯净

传统器物工艺里，「**开光**」指在布满纹饰的器身上留出一块素净空白，专供刻画主体。整器越繁，开光越净。

玉笺的编辑区就是这块开光——**它是整个界面上唯一未经雕琢的净面**。三条理由：

1. **疲劳。** 编辑区是用户连续注视数小时的区域，任何纹理都会累积成视觉噪音。
2. **可读性。** 玉质 / 玻璃的半透明与色偏会直接降低文字对比度，可能击穿 WCAG AA 底线。
3. **导出一致性。** 导出走「直取 ProseMirror DOM」方案，优势是**所见即所得**。编辑区若带材质，导出的干净背景与屏上观感就会脱节——**这个优势会被直接抵消**。

框架层与停靠层加材质不影响导出，因为导出只取编辑区 DOM。

## 2. 材质与高度

### 2.1 高度阶梯：材质 = f(是否叠在内容之上)

| 层 | 元素 | 材质 | 判据 |
|---|---|---|---|
| **E0 内容** | 编辑区画布 | **纯净实色**（无纹理、无渐变、无噪点） | 用户正在读写的对象本身 |
| **E1 框架** | 标题栏、活动栏、侧边栏、大纲、标签栏、状态栏 | **玉质** `.jade`（散射，静态渲染） | 常驻，且**不叠在内容上** |
| **E2 停靠** | 标签面板、内容地图、反向链接、快照（停靠列内） | **玉质** `.jade`（与 E1 同材质） | 常驻，且**不叠在内容上** |
| **E3 浮起** | 下拉菜单、右键菜单、自动补全、编辑区内浮层、统计气泡、凝神退出条 | **玻璃** `.glass`（透视，实时模糊） | **叠在内容之上**，小面积 |
| **E4 模态** | 对话框（帮助 / 偏好 / 外观 / 图床 / 快捷键 / 编译 / 导出预览 / 确认 / 移动 / 冲突）、命令面板 | **玻璃** `.glass` + 最深投影 + 遮罩 | **叠在内容之上**，需用户决策 |

**判据只有一个：这个表面是否叠在内容之上。** 与「常驻还是临时」无关——**那是 v1 选错的轴**。

> **为什么这个轴才对**：凝神退出条是「常驻」的，但它叠在编辑区上、必须半透才不打断沉浸感——按 v1 的轴它该是玉质，显然荒谬。反过来，停靠面板是「可关闭的」，若按「临时」判它就该是玻璃，但它根本不叠在内容上。

### 2.2 为什么 E1 与 E2 同材质却仍是两层

停靠面板（E2）与侧栏（E1）**性质完全相同**、材质必须相同。分层只是为了说明它们在**布局**中的位置不同（E2 在停靠列里与 E1 上下叠放）。它们不需要各自的视觉语言——这正是「**不发明第二套材质**」的意思。

> **一个由材质机制自然给出的细节**：`.jade` 配方顶部有一道 `--material-highlight-top`（5.5% 白，模拟玉器边缘透光）。两片玉上下叠放时，**下面那片的顶部高光天然充当了分段提示**——不必再加一条描边去「划分」。
> 这是本体系的典型做法：**让材质的物理性质去承担 UI 语义，而不是往上叠装饰。**

### 2.3 一次真实的分类纠错：停靠面板的材质

**现象**：左列上半是侧栏（玉质、带噪点、实底），下半是标签面板（玻璃、半透、无噪点）——**同一条 224px 竖列里，材质在中间断开**。右列同理（大纲玉质 + 反链/快照玻璃）。

**根因**：这 4 个面板**原本是浮动卡**。它们自己的样式是

```css
.tags { position: absolute; top: 10px; left: 16px; z-index: 30; width: 320px; … }
```

外加 `class="tags glass"`——它们当初是**叠在内容之上**的浮层，**用玻璃完全正确**。

后来「停靠列」功能把它们收编进 flex 流（`.dock-slot` 用 `!important` 中和了绝对定位与固定宽），**布局语义从「浮起」变成了「停靠」，材质却留在了玻璃**。

**为什么玻璃在这里是错的，而不只是不一致**：`.dock-col` 自身没有背景，玻璃后面就是窗口底色——**它模糊了一个纯色，等于没模糊**，只白拿「更暗 + 没有玉纹」两个副作用。更要命的是 `tokens.css` 自己的段落标题就写着「材质类 · 玻璃（**仅用于小面积浮层**，实时模糊）」——**代码在自己的注释下违规**。

**修法**：4 个面板摘掉 `glass`，材质改由容器 `.dock-slot` 上的 `.jade` 承担。

> **由此确立一条架构规则**：**材质归容器，不归组件。** 因为材质是位置（高度）的函数，而**位置由容器决定**——组件没有资格自证自己浮在什么之上。

**保留的架构债**：这 4 个面板的「浮动身份」还有残骸——`position: absolute` / `top` / 固定宽 / 入场动画 `@keyframes *-in` 全被 `!important` 中和（是死码但无害），`role="dialog"` 也是浮层时代的遗留（已改 `role="region"`）。彻底剥离列入 §9.3。

### 2.4 E3 / E4 的正确率

- **24 个组件**用 `.glass`，全部属浮起层 ✓
- **修正一例反向错误**：`ImgHostSettings` 的对话框曾是 `class="dialog jade"`，且紧跟着一条 `background: var(--hue-editor)` 把它**完全覆盖**——类名成了谎言，观感也和其余 6 个设置浮层不一致。改为 `.glass` 并删掉本地材质声明。
- ⚠️ **这是「配置项存在 ≠ 被消费」的重演**：盘点材质时不能只看「有没有写 class」，要看**这条声明有没有被后续声明覆盖掉**。

### 2.5 玉质配方（`.jade`）

玉的本质是**散射**而非透视：光进入后散开，所以颜色不均匀、边缘略亮、内部有絮状层次。

```
顶部微高光    linear-gradient(180deg, var(--material-highlight-top) 0%, transparent 20%)
左上透光      radial-gradient(120% 62% at 12% 0%,   rgba(var(--hue-tint-1), .13), transparent 62%)
右下反光      radial-gradient(95%  55% at 85% 105%, rgba(var(--hue-tint-2), .10), transparent 58%)
基底          var(--hue-base)
极细噪点      ::after + --noise-texture（feTurbulence data URI，140×140 平铺，opacity .045，overlay）
```

**噪点只属于玉**，玻璃没有。这是两种材质最容易分辨的一处，也是「消除塑料感与渐变色带」的关键——肉眼几乎不可见，但少了它，渐变会起色带、表面会显塑料。

### 2.6 玻璃配方（`.glass`）

玻璃与玉的区别：玉是散射，玻璃是**透视**——它需要有东西可透才有意义。

```
深色  rgba(32,37,38,.66) + blur(var(--material-blur)) saturate(var(--material-saturate))
      border 1px rgba(255,255,255,.09) + inset 0 1px 0 rgba(255,255,255,.07) + 0 18px 48px rgba(0,0,0,.38)
浅色  rgba(245,248,246,.78) + 墨调描边 + 更浅投影
```

**三个细节缺一不可**：

- `saturate()` 提饱和度——纯模糊会发灰，这是「廉价毛玻璃」与「Apple material」的分水岭
- `inset 0 1px 0` 顶部内高光——模拟玻璃上沿的反射
- 1px 亮边框——定义玻璃的边界，纯色背景上尤其重要

> 所有浮层共用这一份配方，**禁止在单个面板里再写一份玻璃背景**。历史上出现过：早期 `.glass` 只写死暗色，亮色下标题栏下拉 / 右键菜单仍是暗玻璃，而「关于」面板自己覆写了亮玻璃，三者质感不一致。

### 2.7 技术约束

1. **窗口级材质跨平台不一致。** 让侧栏真正透出桌面需要系统 API（macOS `vibrancy`／Win11 `backgroundMaterial: mica|acrylic`；**Win10 及以下不支持，自动降级为实色**）。→ 必须接受「Mac 上更通透、Win10 上偏实色」的差异。**玉质配方在降级后依然成立**（渐变 + 噪点照常渲染）——这正是选「玉」而非纯玻璃的好处：对系统能力依赖更低。
2. **窗口内浮层用 `backdrop-filter`**，但只能模糊 DOM 内元素，透不出桌面。
3. **性能**：`backdrop-filter` 在滚动与动画时开销显著。→ 大面积用**静态玉质**（零运行时开销），只有小面积浮层用实时模糊。**这也是 §2.3 判错的代价所在。**
4. **`prefers-reduced-motion`**：关闭动效，但材质保留（材质不是动效）。
5. **⚠️ `backdrop-filter` 会让元素成为「固定定位子元素」的包含块。** 快照面板是 `.snap.glass`，其确认框的 `position:fixed; inset:0` 遮罩会被**困在 340px 宽的面板里**——必须 `<Teleport to="body">` 脱离。
   **对照**：侧栏是 `.jade`（无 `backdrop-filter`）+ `relative`，完全一样的写法就没问题。**别因为「另一处这么写没出事」就判定安全。**

## 3. 刻度

### 3.1 为什么必须有刻度（实测数据）

v2.0 之前，`src/` 里有：

| 维度 | 独立取值数 | 其中「裸写但 = 令牌值」 | 说明 |
|---|---|---|---|
| 字号 | **22** | 200 处 | 含 `10.5 / 11.5 / 12.5 / 13.5` 四种半像素 |
| 圆角 | **24** | 91 处 | `6/8/4px` 裸写 43 处——**恰好就是 `--radius-md/lg/sm` 的值** |
| z-index | **13** | 45 处 | 同一数字承载多个语义（`60` 同时是右键菜单与设置浮层） |

第三个数字最说明问题：**「知道有规范，但规范没被强制」**。
所以病灶不是那 24 个数字，而是「**第 25 个数字可以随手写出来**」。

### 3.2 字号 `--fs-*`

**界面族每级 1px 递进**（UI 需要精确的层级差），**内容族跳跃递进**（标题需要明确落差）。

| 令牌 | 值 | 用途 |
|---|---|---|
| `--fs-10` | 10px | 徽标计数 |
| `--fs-11` | 11px | 微标注、分组标题、键位胶囊 |
| `--fs-12` | 12px | UI 辅助、说明文字 |
| `--fs-13` | 13px | **UI 主文本（默认）** |
| `--fs-14` | 14px | 代码块、对话框标题 |
| `--fs-15` | 15px | 行内代码 |
| `--fs-16` | 16px | 正文 |
| `--fs-18` | 18px | H3 |
| `--fs-22` | 22px | H2 |
| `--fs-28` | 28px | H1 |

**冻结遗留档（只减不增，当前 98 处）**：`12.5px`(42) · `10.5px`(27) · `11.5px`(26) · `13.5px`(2) · `20px`(1)。

> 半像素档在密集 UI 里已形成一套**自洽的「紧凑档」**，收敛会改变全应用文字度量——那是一次**需要单独设计评审的排版改动**，不塞进机械清扫。新代码不得使用。
> **相对单位（`em` / `rem` / `%`）不受此限**：它们天然随上下文缩放，在内容区是正确选择。

### 3.3 间距：不设令牌，只设栅格纪律

**纪律**

- **Y 轴**（上下内边距、行间距）只用 **4 的倍数**
- **X 轴**（左右内边距）允许 **6 / 10 / 14 半格**做视觉配平
- **1 / 2px** 仅限描边接缝与图标光学对齐，**不得当间隔使用**
- **≥ 32px 的间距须为 8 的倍数**（大间距属「区块节奏」，应是刻度的少数几档）
- 一律**整数** px

**为什么间距没有令牌**——一条经过实测后被**否决**的设计：

间距是本项目**唯一从不换档**的维度，而它在源码里有 **620 处**。令牌化会让 `padding: 8px 12px` 变成 `padding: var(--space-8) var(--space-12)`：可读性下降、DevTools 多一跳，换来的只是「能整体改档」这一个**永远不会用到**的能力。

> **由此确立判据**：**令牌的门槛是「这个维度是否存在成体系变化的场景」。**
> 字号有（需整体调密 / 疏）· 圆角有（面层级是固定几档）· 层级有（语义必须命名）· **间距没有——栅格本身就是纪律，纪律用门禁表达即可。**
>
> 这条也回答了「系统化 ≠ 教条化」：一个把 620 处 `8px` 改成 `var(--space-8)` 的「系统」，只是把噪音搬了个位置。

**微间距不设门禁**（≤24px）：那里大量使用 1px 光学补偿（给带 1px 描边的元素减 1px），机械规则会跟设计师的判断打架，收益为负。
**冻结遗留（只减不增）**：`30px`(3) · `78px`(1)。

### 3.4 圆角 `--radius-*`

圆角由**元素所属的面**决定，不由尺寸决定：

| 令牌 | 值 | 面 |
|---|---|---|
| `--radius-xs` | 2px | 面内极小件（进度条、色点内缘） |
| `--radius-sm` | 4px | 面内元素（标签、键帽、徽标） |
| `--radius-md` | 6px | 面上的控件（列表项、按钮、输入框） |
| `--radius-lg` | 8px | **自身成面**（卡片、代码块、小浮层） |
| `--radius-xl` | 14px | 居中大浮层（设置类对话框） |
| `--radius-pill` | 999px | 胶囊（状态、标签芯片） |
| `--radius-full` | 50% | 正圆（色点、单选圈） |

> **`xl = 14px` 是从实作反推的**：8 个设置类大浮层各自独立选了 14px，说明该层级的实际值就是 14——写成 12 反而要把它们全部改掉。
> **规范要向实作里已经一致的部分低头**，只纠正不一致的部分。这是本体系处理「规范 vs 现状」冲突的默认姿势。
>
> **嵌套减速允许**：内嵌件可用 `calc(var(--radius-md) - 3px)` 这类**令牌派生**表达「比父面低一档」——Apple 的做法。

### 3.5 层级 `--z-*`

**禁止再写裸数字。** 同一数字承载多个语义是遮挡事故的根。

| 令牌 | 值 | 语义 |
|---|---|---|
| `--z-local` | 1 | 面内升起：粘性表头、当前项、拖拽占位 |
| `--z-raised` | 2 | 面内第二层：引导线接片、拖拽预览 |
| `--z-sticky` | 10 | 跨面吸附：阅读进度手势区、凝神渐隐幕 |
| `--z-panel` | 30 | 独立面板：停靠面板、侧栏检查面板、统计气泡 |
| `--z-popover` | 40 | 附着浮层：下拉、右键菜单、自动补全、编辑区内浮层 |
| `--z-overlay` | 60 | 居中大浮层：帮助 / 偏好 / 外观 / 图床 / 快捷键 / 编译 / 导出预览 |
| `--z-modal` | 80 | 模态：确认、移动、冲突、命令面板 |
| `--z-toast` | 100 | 操作反馈，**必须压过模态** |

**迁移中修掉的真实事故**：toast 原为 `50`，而模态遮罩是 `80`——**对话框一打开，操作反馈就被遮罩吞掉，用户完全看不见。**

### 3.6 描边

| 宽度 | 用途 |
|---|---|
| `1px` | 常规描边（面板内分隔、卡片边） |
| `0.5px` | 仅高密度区（全局 `button` 的发丝边） |
| `2px` | 仅焦点环与强调竖条（当前项左缘、引用块左缘） |

**颜色分工**：结构性边界（对话框外框、可交互控件圆环）用 `--hue-border-strong`；装饰性分隔用 `--hue-border-subtle`。

### 3.7 图标

**栅格与线宽**（以 `src/components/Icon.vue` 为唯一事实源）：

- 源文件统一 **24×24 viewBox**，`stroke-width: 1.6`，线性、圆角端点、无填充，颜色继承 `currentColor`
- 渲染尺寸走**尺寸刻度**，默认 16 → 等效描边 ≈ **1.07px**（1.6 × 16/24）。这就是「看起来是 1px 发丝线」的来源
- ⚠️ v1 文档此处曾写「统一 16×16 网格、线宽 1px」，与 §5.8 的「24×24」自相矛盾，且与代码不符——**以本条为准**
- 现有 **36 个**图标

**尺寸刻度：12 / 14 / 16 / 18 / 20 / 24**，与同行文字视觉同高——**正文旁 16 · UI 旁 14 · 徽标旁 12**。

> ⚠️ **图标尺寸走 JS 参数（`:size`）而非 CSS 令牌**：它是组件 prop，CSS 变量够不到。故这条纪律靠 Review 保障，**不设 `--icon-*` 令牌**（设了也没人能消费——又一个「配置项存在 ≠ 被消费」）。

### 3.8 动效

```
--ease:      cubic-bezier(0.2, 0, 0.2, 1)      --ease-zen: cubic-bezier(0.22, 1, 0.36, 1)
--dur-fast:  120ms  悬停、按下
--dur-base:  180ms  面板展开、菜单
```

只允许 `opacity` 与 `transform` 参与动画（避免重排）。
**必须支持 `prefers-reduced-motion`**：该偏好开启时全部时长归零，但材质保留（材质不是动效）。

> **为什么只有两级**：曾设过 `--dur-slow: 280ms`（侧栏收起、对话框），但它**从来没有消费者**——
> 全项目唯一的 `280ms` 出现在 `zen.css` 的 `transition: opacity 120ms var(--ease-zen) 280ms`，
> 那是**延迟**（stagger），不是时长。用 `--dur-slow` 去命名一个延迟是语义错误，
> 于是它被删掉、刻度收敛为两级（见 §9.2 规则⑦）。
> **凝神的多幕编排（幕一~幕四）用的是显式延迟**，`120ms` 时长 + `60/80/180/280ms` 延迟错峰——
> 这是一段手工调过的编排，不属「档位」，不该被令牌化。

### 3.9 结构尺寸

```
高度  --h-titlebar 38px · --h-crumb 30px · --h-tabbar 34px · --h-statusbar 26px · --h-row 28px
宽度  --w-outline 196px（CSS 令牌，不可拖拽）
列宽  --w-column clamp(700px, 56vw, 920px) · --w-column-zen clamp(760px, 62vw, 1000px)
```

> **注意侧栏宽度不在这里**：侧栏可拖拽（180–360px），其宽度是**运行时状态**
> `useWindowLayout.ts` 的 `DEFAULT_SIDEBAR_WIDTH = 224`，经 `:style` 注入并持久化到 `session.json`。
> 曾有一个 `--w-sidebar: 224px` 令牌，但**全项目零引用**——CSS 改不动它，JS 也不读它，
> 它只是一份会误导人的副本（已删，见规则⑦）。
>
> **判据**：**静态的布局常量走 CSS 令牌，可交互的运行时尺寸走状态**。
> 同一个数字出现在两处而只有一处生效，就是下一次「改了没反应」的种子。

## 4. 色相：窑色系统

### 4.1 三层令牌（换皮肤只改第三层）

| 层 | 内容 | 换皮肤时 |
|---|---|---|
| **结构层** | 尺寸、圆角、动效时长、字体、层级、**刻度** | ❌ 不动 |
| **材质层** | 噪点强度、模糊半径、饱和度、高光透明度、渐变位置与角度 | ❌ 不动 |
| **色相层** | 基底色、透光色 ×2、强调色、编辑区色、文本三级、状态色 | ✅ **只换这一层** |

**新增一套皮肤 = 加一段 CSS 变量块，零结构改动、零材质重做。**

### 4.2 皮肤目录

| 皮肤 | 来源意象 | 强调色（深 / 浅） | 状态 |
|---|---|---|---|
| **青瓷 Celadon** | 龙泉窑梅子青 | `#5FA8A0` / `#248077` | ✅ 默认 |
| 天青 Sky | 汝窑雨过天青 | `#5E9DBE` / `#2B7BA8` | ✅ |
| 月白 Moon | 月白釉，极淡蓝白 | `#93A7B4` / `#5A7180` | ✅ |
| 黛 Dai | 黛紫，墨青紫 | `#8B7CB8` / `#6A5A9E` | ✅ |
| 琥珀 Amber | 老蜜蜡，暖调 | `#C79A4E` / `#9A6F24` | ✅ |

五套 × 明暗 = **10 套**，均通过 WCAG AA（强调色对比度 4.6:1 – 6.7:1）。
取色来自**中国传统窑色系**而非凭空调配——有实物质感参照的颜色更耐看，也更有辨识度。

### 4.3 令牌清单（真实现状，以 `tokens.css` 为准）

**色相层**（每皮肤一份，选择器 `[data-skin='x'][data-mode='y']`）
`--hue-base` 窗口底 · `--hue-editor` 编辑区 · `--hue-tint-1/2` 透光色 · `--hue-accent` · `--hue-text-1/2/3` · `--hue-danger` · `--hue-success` · `--hue-active`（16%，hover/聚焦） · `--hue-border-subtle` · `--hue-code` / `--hue-code-fg` · `--hue-highlight` · `--hue-key` · `--hue-list-marker` · `--hue-scrollbar-*`

**派生层**（`[data-skin][data-mode]` 追加，跨皮肤一致、仅按明暗取值）
`--hue-surface` / `--hue-surface-2` 抬高表面 · `--hue-on-accent` 强调按钮上的文字 · `--hue-shadow-1/2` · `--hue-selection`（34% / 30%） · `--hue-border-strong` 结构边界 · `--bg-hover` 中性悬停底 · `--hue-mark` / `--hue-key` 兜底值

**材质层**（`--material-*`，永不随皮肤变）· **结构层**（`--fs-*` / `--radius-*` / `--z-*` / `--dur-*` / `--ease*` / `--font-*` / `--h-*` / `--w-*`）

> ⚠️ `--bg-hover` 必须**按明暗分两份**定义。历史上只有一份 `rgba(255,255,255,.05)`——亮色下等于「白底上叠白」，**23 处 hover 全部失效**。

### 4.4 四类必须记住的令牌陷阱

**① RGB 分量 ≠ 完整色值。**
`--hue-tint-1` / `--hue-tint-2` / `--hue-mark` / `--hue-key` 存的是 **`126,196,182` 这样的分量**，当背景必须包 `rgb()` / `rgba()`。
历史上 3 处写成 `background: var(--hue-mark)`——**CSS 直接判非法、静默丢弃**，于是徽章透明、色点消失、白字悬空。

**② 伪令牌 = 静默失效。**
`var(--名字)` 里名字从未定义时，CSS **丢弃整条声明**，不报错不警告。
v2.0 清掉 12 个；其中 `--hue-border-default` **连 fallback 都没有**，3 处边框**根本没画出来**。

**③ 死 fallback = 谎言。**
`var(--radius-lg, 14px)`：`--radius-lg` 明明是 8px，fallback 写 14px——**它永远不会生效，却会误导下一个人**。已有 7 处清除。

**④ 零引用令牌 = 能算出值的谎言。**
定义了、却全项目没人用（如曾有的 `--hue-bar`：**5 套皮肤 × 明暗共 10 处声明、引用 0 处**；
`--w-sidebar`、`--dur-slow` 同理）。它比 ② 更阴——**不会报错、也确实能算出颜色**，
所以你根本不会怀疑它；但它通常只在 `:root` 写了一档，**不参与主题切换**，
谁照着用了，谁就在亮色/其他皮肤下拿到一个错值。
由**规则⑦**兜底；唯二的例外是①动态注入的令牌族（`--fog-*`）②对外契约令牌（`--crepe-*`，消费者在 `node_modules` 里）。

> 这四类事故的共同点：**改了看不出来、测试全绿、只有人眼（还得是特定皮肤/明暗下）能发现。** 所以它们必须由**门禁**兜底——这正是 §9 存在的理由。

### 4.5 可访问性下限（§1.2 推论二的落地）

- 正文对比 ≥ **4.5:1**；大字号与**图形**（图标、边框、圆环）≥ **3:1**
- **装饰可以低对比，功能不可以**：分隔线、噪点、底衬渐变随便退；但**文字、图标、可交互控件的边界**必须可见
- 三级文本用 `--hue-text-3`，不再更低（v1 曾定 `#83848C`，实测 4.32:1 未达 AA，已上调）
- 已实测修正的两处：① 强调 / 危险按钮文字写死 `#fff` → 暗色青瓷上仅约 **2:1** → 改 `--hue-on-accent`；② 未选中的单选 / 复选框圈用 `--hue-border-subtle`（约 **1.2:1**）→ 改 `--hue-border-strong`（≥3:1）
- 文本选区用 `--hue-selection`（34%），**不是** `--hue-active`（16% 是 hover / 聚焦用的，作选区太淡、几乎看不见）

### 4.6 应用图标

品牌名「玉笺」，图标取**玉质圆角 tile + 笺（笔记）slip** 两层意象：

- **源文件** `build/icon.svg`（512×512，玉质渐变 + 釉面高光 + 白色笔记 slip + 玉色文本行）
- **产线** SVG 经 `@resvg/resvg-js`（纯 WASM）栅格化为 16/24/32/48/64/128/256/512 多尺寸 PNG，再按 PNG-in-ICO 组装 `build/icon.ico`（Windows）；另导出 `build/icon.png`（1024，macOS / Linux）
- **接入**：开发期 `BrowserWindow({ icon: build/icon.png })`（`existsSync` 兜底）；打包由 `package.json` 的 `build` 配置注入
- **原则**：图标只表达品牌色（青瓷玉），**不随皮肤变化**——皮肤切换只改应用内 CSS 变量

### 4.7 切换机制

- 根节点挂 `data-skin` 与 `data-mode` 两个属性（**写在 `src/index.html` 的 `<html>` 上，首屏即到位**，不依赖 JS），CSS 变量随之切换
- 切换皮肤**不需要重建编辑器实例**（Crepe 只读 CSS 变量，不读具体色值）
- 选择持久化在 `localStorage`（键 `yujian.appearance`；见 `src/appearance.ts`）
- 「跟随系统」：`data-mode` 由 `prefers-color-scheme` 驱动（`matchMedia` 监听，实时跟随）
- 设置面板中皮肤预览用**真实材质缩略图**（`.swatch.jade`），不用色块——色块表达不出玉的质感

**三层用法**：`role` 由高度决定，不由组件决定——

- E2 停靠 → `role="region"`（或让它继承宿主语义）
- E3 居中浮层 → `role="dialog"` + `aria-modal="false"`（不锁背景）
- E4 模态 → `role="dialog"` + `aria-modal="true"` + 焦点圈禁 + Esc 关闭

⚠️ 这是一条**踩过坑**的规则：`TagPanel` / `MocPanel` / `BacklinksPanel` / `SnapshotPanel`
曾同时挂 `class="glass"` 和 `role="dialog"`——它们是 flex 停靠流里的面板，
却从「浮动卡片」时代继承了玻璃材质与模态语义。**读屏会把它当弹窗播报，而它其实常驻。**
修正过程见 §2.3。而 `ImgHostSettings` 走了反方向：真对话框却自挂 `.jade` + 一条本地 `background`。

> **推论**：材质与 `role` 都应写在**容器**上，组件不该自带。组件自带材质时，
> 它在 E2 位置就是错的；容器接管后，同一个组件放进任何高度都自动正确。

### 5.2 浮层宽度阶梯（**指南，刻意不设令牌**）

| 档位   | 宽度  | 判据                    | 组件                                       |
| ---- | --- | --------------------- | ---------------------------------------- |
| 极小   | 320 | 二选一确认，只有一个问题          | `ConfirmDialog`                          |
| 小    | 360 | 单列设置，无列表              | `PreferencesSettings`、`AppearanceSettings`、`MoveDialog` |
| 中    | 440 | 表单，字段 ≤ 6 个            | `ImgHostSettings`                        |
| 中宽   | 520 | 双栏内容，带说明段落            | `HelpPanel`                              |
| 宽    | 540 | 列表 + 表单混排              | `CompilePanel`                           |
| 宽    | 560 | 搜索框 + 结果列表（需要一行放下路径）  | `ShortcutsSettings`、`CommandPalette`     |
| 宽    | 720 | 左右对照（diff / 冲突）        | `ConflictDialog`                         |
| 极宽   | 880 | 工作台：预览 + 控制条并置        | `ExportPreview`                          |

**为什么宽度不设 `--w-dialog-*` 令牌**——这与 §3.3 间距不设 `--space-*` 是同一条理由：
宽度是**内容驱动的一次性决策**，不是会随皮肤/主题变化的量，也不存在「同一语义值散落多处」。
8 个浮层就是 8 个内容形态；把它们压成 4 档只会让「确认框 880px」这种荒谬组合变得合法。
令牌化在这里买不到一致性，只会买到一个新的谎。

**离群值说明**（`520` / `540` 与 `560` 差 20–40px，是历史上各面板独立演化留下的）：
它们是**已知的离群**，收敛会改动 8 个浮层的实际版式，属于一次需要单独评审的排版改动，
不塞进机械清扫——与 §9.3 对待半像素字号的态度一致。若要收敛，目标是 4 档：
`360 / 440 / 560 / 880`，并在收敛时同步本节表格。

所有浮层统一：`max-width: calc(100vw - 32px)`（`CommandPalette` 用 `24px`、`ExportPreview` 用 `48px`，因内容更宽需要不同留白）；圆角 `--radius-lg`（设置族）或 `--radius-xl`（`ImgHostSettings`）。

| 项    | 规格                                                                                                        |
| ---- | --------------------------------------------------------------------------------------------------------- |
| 行高   | `--h-row` 28px（触控目标下限）                                                                                    |
| 缩进   | 每级 14px（行内边距 `8 + level × 14`）                                                                            |
| 层级引导 | VS Code 式引导线：垂直引导线从父行**箭头中心**贯穿整棵子树（仅展开且有子节点时出现），子行带 9px 水平接片；线与箭头列严格对齐（箭头中心 = `13 + level × 14`） |

> **为什么给文档也配 doc 图标**：图标列恒定后（chevron → 图标 → 名称），文件行与目录行的排版节奏完全一致、缩进与引导线天然对齐；单字形 doc 图标不携带格式信息（库内几乎全是 `.md`），只是补全视觉节奏。

### 5.10 块操作手柄（一致性左轨）

* **问题**：Crepe 用 floating-ui 以 `placement:'left'` 把块手柄（`+` 增加 / `⠿` 拖拽）放在「块自身左缘左侧」，并带 `flip()`。结果：窄窗时块左缘贴边 → 手柄 `flip` 到**右侧**；列表等缩进块 → 手柄右移，整列手柄参差错落。
* **方案**：不再用全局 `left` 覆盖（那会忽略编辑区 `84px/30px` 的非对称内边距，手柄反而压到文字）。**完全保留 floating-ui 算出的块左缘**，仅用 `transform: translateX(-12px)` 把手柄左移 12px 落进固定沟槽——缩进块的手柄随之右移、始终在块左缘左侧（Notion 式），**永不右翻、绝不遮字**；动态 `top` 仍跟随当前块。
* **视觉**：玉质玻璃药丸（`--radius-md` + `--hue-surface` 实底 + 发丝边 + `--hue-shadow-1`），图标默认 `--hue-text-3`、悬停/激活变 `--hue-accent`
* **配套**：编辑区左内边距 30px → **84px**，刚好容纳手柄（约 64px 宽）+ 12px 呼吸缝
* 实现：`src/styles/editor.css` 的 `.milkdown-block-handle` 段 + `.ProseMirror` 的 `padding-left`

### 5.11 编辑区浮层：药丸托盘**必须同源**（产品级约定）

Crepe 自带的托盘**只给图标不给文案**（部分节点连 `role` 都没有，读屏不可达）。

并统一视觉：`--hue-text-2` / opacity .9 图标 → hover `--hue-active` 底 + accent 图标；圆角恒定 `--radius-md`（6px）。

**覆盖清单**（改 Crepe 版本先复核顺序约定）：
① 块操作手柄 ② 表格手柄弹出条 + 细线增行增列 ③ 公式符号条 ④ 图片块 / 链接浮层裸图标 ⑤ **代码块工具条**（预览切换钮 + 语言搜索清空）

🔴 **任何一处新增托盘/按钮，其余处必须同步**——否则又出现「一个有提示一个没有」。
🔴 纯交互触发的浮层（代码块切换钮/清空、图片上传、链接悬停）**既不在 `create()` 也不在 `markdownUpdated` 上**，

## 9. 治理：让准则有牙齿

> **这一章是 v2.0 与 v1 的分界线。**
> v1 的病不是「写得不好」，而是**写完就没人管**——`--space-*` 甚至只活在文档里、源码从未存在过。
> 一个没有强制机制的规范，平均 3 个月后退化成「一份描述过去的文档」。

### 9.1 闭环：原则 → 刻度 → 强制

```
§1 原则（光只从浮起处透出）
   ↓ 可量化
§3 刻度（--fs / --radius / --z / --hue-*）
   ↓ 可检查
§9 门禁（scripts/check-design.mjs，进 CI）
   ↓ 违反
构建失败 + 精确文件:行号 + 修复提示
```

缺任何一环都会断：**没有刻度的原则**是口号（设计师各凭感觉）；**没有门禁的刻度**是建议（40 个组件各自即兴发挥）。
这正是 v1 的病根。

### 9.2 七条规则（全部进 CI）

| # | 规则                              | 为什么它是事故而不是风格问题                        |
| - | ------------------------------- | ------------------------------------- |
| ① | **令牌必须已定义**（含 `var(--x, fb)` 里 `x` 不存在） | 伪令牌会让 CSS **静默丢弃整条声明**：边框不画、背景不变、hover 不动，不报错不警告、测试全绿 |
| ② | `z-index` 必须引用 `--z-*` 语义阶梯     | 裸数字遮罩事故（新增浮层压住 Toast）无法被评审发现          |
| ③ | `border-radius` 必须引用 `--radius-*` | v1 实测 24 种圆角，肉眼可见的「不齐」                 |
| ④ | 颜色不得写死 hex（排除 `tokens.css` 与导出模板） | 写死色在另一套皮肤 / 明暗下必然错（`#6fcf97` 在琥珀皮肤上发灰） |
| ⑤ | 字号须为 `--fs-*` / `em` / 冻结遗留值    | v1 实测 22 种字号                          |
| ⑥ | 间距须整数 px；≥32px 须为 8 的倍数          | 大间距是「区块节奏」，应是刻度的少数几档，不是即兴值            |
| ⑦ | **令牌必须有消费者**（零引用即报红）           | 与 ① 互为反面：① 抓「用了不存在的」，⑦ 抓「存在了没人用的」。零引用令牌**能算出值、不报错**，只是不参与主题切换 → 照用必错 |

规则 ⑤⑥ 用**冻结遗留值**（半像素字号 5 档、离群大间距 2 档）而非一刀切——见 §9.3。
规则 ⑦ 有两类**经过论证的例外**：动态注入的令牌族（`--fog-*`，由 JS `setProperty` 拼名）与
对外契约令牌（`--crepe-*`，消费者是库在 `node_modules` 里的 CSS，零引用是正常状态）。

### 9.3 冻结与棘轮：只减不增

机械清扫**不该顺手改版式**。两类值被显式冻结：

* **半像素字号层**（`12.5 / 10.5 / 11.5 / 13.5 / 20px`）：这是密集 UI 里一套自洽的「紧凑档」，收敛会改变全应用文字度量——属于需要单独设计评审的排版改动，不塞进机械清扫。
* **离群大间距**（`30 / 78px`）：大间距属区块节奏，应是少数几档，但此刻收敛同样会挪动版式。

它们以**计数为基线、只减不增**（同 `check-structure.mjs` 的 `any` 门禁纪律）。
微间距（≤24px）**不设门禁**：那里大量使用 1px 光学补偿（给带描边的元素减 1px），机械规则会跟设计师的判断打架，收益为负。

**放宽必须显式改脚本常量并在提交信息里说明原因**——让「破例」留下痕迹。

### 9.4 反例防护

* **扫描面按目录组织**（`src/`，豁免 `src/export/`），不写死文件路径——否则组件一拆分，门禁静默失效
* 扫描前剥离 `/* */` 与 `//` 注释（保留换行以维持行号）——注释里出现 `var()` / `z-index` 会造成假阳性
* **每条规则都做过「注入故障 → 期望报红 → 还原 → 复绿」验证**。没验证过的规则等于空转：它会一直绿，而你以为是「大家都守规矩」

### 9.5 怎么加一条新规则

1. **先在一处观察到重复的即兴发挥**（不是「我觉得应该有」，而是「实测 12 处不一致」）
2. 能收敛的**先收敛**（迁移脚本），收敛不了的**冻结计数**
3. 写成规则，跑全量，确认基线为绿
4. **注入一次故障**，确认报红且提示能定位到文件:行号
5. 还原，确认复绿
6. 在 `docs/UI-DESIGN.md` 与提交信息里记一笔：**为什么**这条规则存在（否则下一个人只会想绕过它）

### 9.6 什么时候允许破例

门禁是**下限**，不是审美上限。以下情形**应当**破例，并在代码里写清理由：

* 独立样式上下文（导出 HTML 模板自带字体栈与调色，不参与应用主题）→ 已列入 `EXEMPT`
* 需要精确控制且令牌会引入误差的光学补偿
* 与第三方库内部 DOM 对齐的一次性数值（Crepe 浮层定位等）

**破例的正确形态**：在代码注释里写「为什么是它、而不是令牌」，而不是默默写一个魔法数字。
`ImgHostSettings.vue` 里那条注释就是范例——

```
/* 材质由 .glass 单一来源提供（与帮助/偏好/外观/快捷键同款玻璃浮层）。
   此处曾写 `class="dialog jade"` + 本条 background：jade 被这条 background 完全覆盖，
   类名成了谎言，观感也与其他 6 个设置浮层不一致。设计规则见 docs/UI-DESIGN.md §2。 */
```
