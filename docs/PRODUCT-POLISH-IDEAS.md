# 玉笺 · 产品打磨方向（同行案例对照）

> 目的：对照同行（Typora / Obsidian / Zettlr 等）的成功与失败，系统性思考「如何把玉笺做得更好」。
> 结论先行：**玉笺的方向已被同行验证是对的**（Typora 的写作体验 + Obsidian 的知识管理），真正的风险在于**Phase 3 建索引层时会重蹈 Obsidian 的规模化覆辙**。
> 本文供 Phase 3 及后续打磨参考，不替代 `docs/PHASE3-PLAN.md`（后者是执行计划，本文是方向判断）。

***

## 1. 同行案例：他们做对了什么，又在哪里翻车

### Typora —— 「写作体验」的标杆

**做对了（值得学）**：

* **输入即排版**：去掉预览窗口、模式切换器、源码符号，只留实时预览。用户评价「打开就能写，没有学习成本，用过的都回不去」。
* **极简到几乎无界面**：没有工具栏、没有侧边栏堆叠，打开就是一张白纸。
* **打字手感和延迟控制做到极致**：用户连用 4 年从未卡顿——**本地软件的性能就是护城河**。
* **复杂元素的「临时编辑界面」**：代码块、表格提供专注的编辑区（可视化调列宽、语言高亮），而不是让人在源码里数竖线。
* **自定义 CSS 主题**：高度可定制，社区主题生态繁荣——**低成本高收益**的个性化方案。
* 细节：自动编号、`[TOC]`、内部链接跳转、脚注悬停显示、CJK 正确渲染。

**短板（玉笺的机会）**：**完全没有知识管理**——无标签、无双向链接、无数据库。用户评价「这是它的局限，也是它的纯粹」。

### Obsidian —— 「知识管理」的标杆，也是规模化的反面教材

**做对了**：双链 + 反链 + 图谱 + 插件生态 + Daily Notes + 模板，把「本地 Markdown 文件夹」变成了知识库。

**翻车的地方（玉笺必须避开，有实证）**：

| 失败点                                                                           | 实证                                                                       |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| **规模性能崩塌**：元数据全量重算阻塞渲染主线程                                                       | 官方论坛 bug 报告：约 10,500 文件的库，`getAllPropertyInfos()` + `updatePropertyInfoCache()` 占 CPU 采样 **96.76%**，**每 2 秒冻结渲染线程约 280ms**；重建缓存期间反而流畅，一完成就复发 |
| **模糊搜索不可扩展**：5000 笔记开始软卡顿，10000+ 被开发者承认「Very Bad」                             | 社区只能靠插件「抽样搜索」绕过，牺牲了搜索完备性                                                 |
| **内存爆炸**：5000 笔记 >1GB；20000 笔记 + 50000 图 → **6–10GB**，逼近 V8 上限                | 大量来自索引缓存的元数据                                                            |
| **数据完整性脆弱**：文件系统无跨文件原子操作；一次保存可能写多个文件（md + 索引 + 历史），中断即不一致；**无 vault 级内容完整性校验** | Sync 冲突解决是设备级配置，不同设备配置不一致会产生冲突甚至数据丢失；重命名崩溃会留下「两份状态」                      |
| **表格损坏**：含大量表格的笔记在反复操作后损坏                                                    | 社区反复报告                                                                  |
| **插件生态是双刃剑**：性能问题排查的标准答案是「先禁用插件逐个排查」                                          | 10 个插件即可让 1000 笔记的库明显变慢                                                 |

> **对玉笺的直接启示**：玉笺**不做插件市场**（ARCHITECTURE §1.3）是正确决策，避开了 Obsidian 最大的性能不确定性来源。但 Phase 3 的索引层若设计不当，会在没有插件的情况下重演同样的崩塌。

***

## 2. Phase 3 索引层的「防坑设计准则」（最高优先级）

Phase 3 要建 vault 级索引，这正是 Obsidian 的翻车点。以下准则应写进实现约束：

1. **严格增量，禁止全量重算**：只在 watcher 事件里重解析变动文件。**绝不能**有「遍历全库重算属性」的周期任务（Obsidian 的 280ms 卡顿就是这么来的）。
2. **索引只存轻量元数据**：路径 / `mtime` / 标题 / 链接 / 标签 / 少量 headings。**不缓存正文、不索引全文**（全文检索交给按需扫描，或受控的小体积索引）。索引体积必须设上限。
3. **不在渲染主线程做全库工作**：索引构建维护放主进程；渲染进程只消费增量结果。
4. **设性能预算并实测**：目标——vault 5000 文件时，输入延迟无可感知退化；索引内存 < 100MB。每次批次完成用大样本库实测，别只看 typecheck。
5. **完整性自检工具**：Obsidian 缺的就是这个。提供 vault 级自检（索引与磁盘不一致、孤儿快照、断链、缺失附件），可一键修复/重建。
6. **保持原子写优势**：主进程 `session.ts` 已用 temp + rename 原子写，这是相对 Obsidian 的**结构性优势**，不要为了索引而引入多文件非原子写入。
7. **表格稳定性压测**：Obsidian 有表格损坏先例，玉笺应针对「反复增删行列/合并/撤销」做压测。

## 3. 差异化护城河：中文排版（同行普遍没做好）

Typora / Obsidian 均由英文世界主导，中文排版普遍粗糙。而中英混排规范是**有明确标准**的：W3C《中文排版需求》§3.2.2、GB/T 15834—2011《标点符号用法》、少数派风格指南。

**关键规范**（研究确认）：

* 汉字与英文字母/数字之间应加**半角空格**（`中文 ABC 中文`，而非 `中文ABC中文`）。
* **理想情况应由排版引擎自动加入，宽度为 ¼ em**——但绝大多数环境（含网页）做不到，只能退而求其次手动插空格。
* 英文/数字与**全角标点**之间不加空格（`有了 Markdown,可以…`）。
* 行内代码前后加空格；破折号、省略号前后加空格；引号括号另有规则。
* 中文用**全角标点**；中文斜体排版难看，规范建议改用**颜色或着重号**而非 `font-style: italic`。
* 避头尾：行首不能出现点号、逗号、句号、结束引号/括号。

**玉笺可以做的（分两类，注意红线）**：

* **A. 渲染层视觉优化（零风险，不碰源文件，守往返保真红线）**——强烈建议优先做：
  * 中英混排**自动视觉间距**：渲染时插入 ¼ em 的间距（ProseMirror Decoration 或 CSS），**源文件一个字都不改**。这正是规范说的「应由排版引擎自动加入」，而主流编辑器都没做。
  * **中文斜体改用颜色/着重号**（中文斜体公认难看）。
  * 标点挤压、避头尾规则、中英文字体 fallback 搭配、中文行高/段间距优化。
* **B. 显式格式化命令（用户触发，明确改写，不违反红线）**：
  * 「排版规范化」命令：中英混排补空格、半角标点转全角、清除多余空格。用户主动执行且可撤销，与「自动保存时改写」有本质区别。
  * 可作为**文档 lint** 的一项：提示「此处中英之间缺空格」而不自动改。

> ⚠️ **红线提醒**：**绝不能**在保存时自动改写用户源文件来「补空格」——这直接违反往返保真红线（未编辑文档保存必须一字不改）。所有自动行为必须只在渲染层，改写必须是用户显式触发的命令。

## 4. 其余打磨方向（按 ROI 排序）

### 高 ROI

1. **数据完整性（笔记软件的命根）**
   * vault 级自检与修复（见 §2.5）。
   * **整库备份**：现有快照是单文件级，缺少「一键整库备份/恢复」。
   * **外部修改冲突检测**：chokidar 已能感知外部改动，但「我正编辑 + 外部也改了」的冲突如何呈现、是否保留双方版本，需要明确策略（Obsidian 在这一点上被诟病）。
2. **大文档性能**：10 万字以上文档的编辑流畅度（虚拟滚动/分块渲染）。Typora 的「4 年从不卡顿」是用户忠诚度的核心来源。
3. **写作体验细节（学 Typora）**：
   * 复杂元素的「临时编辑界面」：表格可视化调列宽、代码块专注编辑、公式编辑器。
   * **键盘优先**：命令面板（Ctrl+Shift+P）+ 快捷键可自定义。
4. **个性化（低成本高收益）**：**用户 CSS 片段 / 自定义样式**——Typora 与 Obsidian（snippets）都证明这是最受欢迎的能力之一，且实现成本远低于插件系统。

### 中 ROI

5. **技术写作特化（护城河）**：
   * **参考文献/引文管理**：BibTeX 导入、引用样式（GB/T 7714、APA）、Zotero 联动——Zettlr 已在学术写作场景验证的刚需。
   * **文档 lint 扩展**：现有断链检查可扩展为——中英混排检查、术语一致性、标题层级跳跃、重复标题。
6. **发布闭环**：vault → 静态站点（博客/文档站）导出。Obsidian Publish / Quartz 已验证需求。
7. **中文分词**：改善双击选词（现在双击中文可能选中整段），并提升中文搜索质量。

### 明确不建议做

* **云同步 / 协作**：需后端，ARCHITECTURE §1.3 已明确另立项目。Obsidian Sync 的冲突问题也说明这块水很深。
* **插件市场**：性能不可控（Obsidian 教训）。用 CSS 片段 + 导出模板满足个性化。
* **AI 辅助**：无可用 API，Crepe 接口保留即可。
* **移动端 / 实时协作**：另立项目量级。

***

## 5. 一句话总结

> 玉笺要赢，不是靠功能比 Obsidian 多，而是靠：**Typora 级别的写作手感 + Obsidian 级别的知识管理 + 同行都缺的中文排版与数据完整性**——并且从第一天起就把「规模下的性能与可靠」当成硬约束，而不是等用户涨到 5000 篇笔记再补课。
